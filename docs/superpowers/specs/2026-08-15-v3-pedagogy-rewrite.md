# v3 全书重写：以「写书前先读懂系统」为第一原则

> 立项：2026-08-15，用户决策。分支：`vllm-book-v3-rewrite`（v2 封版于 `vllm-book-v2-rebuild` 作对照基线）。
> 用户的诊断（原话摘要）：「写书之前没有仔细调研过架构和讲法……像一本字典只能查，根本没法牵引读者帮读者构建体系。好的叙述方式：先完全了解项目、站在高处看到系统架构、有整体视角、看得到从哪条路走进来学习难度最合适，然后站在读者视角真诚地为读者阶梯式管理认知模型——从简单的宏观入手，慢慢拆解深入细节，而不是上来就淹没在海量细节中。」

## 0. 病根（为什么 v2 失败）

| # | 病根 | v2 的症状 |
|---|------|----------|
| 1 | **图系不是缩放关系** | 同一架构三套并行画法：arch-model（开篇五层带）+ chapter-map（每章一张独立剖面）+ 正文机制图，互相无粒度嵌套；ch01 与 ch02 的「同一张图」对不上 |
| 2 | **大纲是字典不是路径** | 39 章按模块分区排（config→entrypoints→input→…），Part 是子系统分区、不是认知台阶；每章「模块解读」体，没有问题驱动 |
| 3 | **无读者认知阶梯管理** | 作者全知视角平铺；概念在读者困惑点没有被接住；开篇即细节淹没 |

**根因**：动笔前没有做「完全理解系统 → 获取整体视角 → 分析最佳学习路径 → 设计认知阶梯」这四件事，直接从素材收集（dossier）跳到了写作。

## 1. 参照系：vllm-podcast 的方法论（E:\Laboratory\Devpodcast\shows\vllm-podcast）

播客以本书 v2 为书源，但它在「讲法」上做对了四件事，全部采纳：

1. **一张架构图贯穿全季**（`C:\Users\zhou.jianqi\Desktop\vllm架构.excalidraw`：API 进程 / 引擎进程 / 三段式 / ZMQ 边界 / user→sse 出口）——所有期都指着这张图讲。
2. **季规划 = 学习路径**（`season/season-plan.json`）：每期一个 hook 大问题（「俩字凭啥跑两趟跨进程快递？」「调度器不认请求数只认 token 数」「显存是主角」…）+ depends_on 依赖链 + foreshadow/payoff 伏笔登记回收。
3. **读者代言人**（阿哲）实时打断（「等等，『同步』是什么意思？」）——认知阶梯的实时管理。
4. **v0→v1 演进叙事**：先讲旧设计是什么→痛点→为什么逼出新设计——设计决策的 why 链。

播客 5 期 × 5 台阶：三段式解耦 → 引擎心跳 → 显存与持久批次 → GPU 执行管线 → 智能采样。**这个台阶划分是 Phase 1 的重要输入**（但书比播客深，台阶会更多、每台阶内多层缩放）。

## 2. 四阶段（严格顺序，每阶段有硬验收，前一段未验收不进下一段）

### Phase 0：架构深读（先完全理解系统）
**目标不是收集素材**（dossier 已有），是**理解系统**——从设计者视角回答每个子系统的 why。

产出：
- `book/cartography/ARCHITECTURE.md`：深度架构文档。主轴 = 一个请求的一生（数据流），每个设计决策一条 why 链：旧设计是什么 → 痛点（吞吐/延迟/显存/并发哪个指标被卡）→ 为什么这个方案胜出 → 代价是什么（每个设计都有代价，诚实记录）。
- `book/cartography/L0-architecture.svg/png`：**唯一权威全书架构图**（L0）。要求：数据流为主轴（user→API 进程→EngineCore 进程→GPU→回程）；进程边界/异步边界/数据所有权显式；v2 的 21 个子系统全部挂图、各标「在第几 Part 打开」；它是 excalidraw 那张的完整版（那张只画了核心路径）。
- 每个子系统一张「深读卡片」：它解决什么问题、不它存在会怎样（反事实）、它的上下游契约、首读章应在哪（pedagogy 建议）。

验收（Lead + 用户）：L0 图 10 秒能看懂主线；ARCHITECTURE.md 的每条 why 链能说服「一个懂后端但不懂 AI 的读者」。

### Phase 1：学习路径设计（整体视角 + 最佳路径）
产出 `book/cartography/pedagogy-plan.json` + 大纲（用户审批后才进 Phase 2）：
- 全书重组为 **5–8 个 Part = 5–8 个认知台阶**，每 Part 一个 hook 大问题（一句话，能戳中困惑）。
- 依赖图显式（depends_on）；伏笔登记/回收（foreshadow/payoff）自顶向下设计——不是写作中顺手埋。
- **每章定义「L0 图上的缩放路径」**：本章是 L0 →（L1 Part 图）→ L2 章图的哪一块放大。
- 概念首现表：每个非常识概念在哪章首立、之前靠什么铺垫——阶梯不跳级。
- 章数自由重组（合并/拆分/重排 v2 的 39 章），预计 25–35 章。

### Phase 2：图系重构（三层缩放，同一张图）
- **L0**：全书唯一架构图（Phase 0 产出）。
- **L1**：Part 图 = L0 的**局部放大**（同一坐标系、同配色、同图例、同术语）。
- **L2**：章图 = L1 的局部放大（源码级细节：类/方法/数据结构）。v2 的 arch-model 渲染器改造成本体系；**chapter-map 图系废弃**。
- 硬规则：任何两张图必须是「放大镜关系」，绝不允许同一架构两种画法（v2 病根 1 的结构性根治）。实现方式：一套图源数据（cartography）+ 一个分层渲染器，L0/L1/L2 从同一数据按 zoom 裁切渲染。

### Phase 3：逐章重写
- 新 writer 契约：hook 开篇（本章回答什么大问题）→ 先 L0 定位再 zoom-in → 阶梯展开（每引入一个概念，先答「为什么需要它」）→ 收尾回指（本章在 L0 图上点亮了哪块 + 下一块预告）。
- v2 源码解读段**择优迁移**（经 reviewer 核实逐段对照 pin 源码后迁移），叙事骨架/开篇/图全部重写。
- pipeline / 8 角色 / linter 复用；盲审增加「认知阶梯」维度（读者代言人视角审：哪里跳级了、哪里没接住）。

## 4. 硬规则（v3 新增，写进 CLAUDE.md / INSTANCE.md）

1. **一张图原则**：全书只允许一种架构画法（L0/L1/L2 缩放体系）；任何新图必须能回答「它是 L0 哪一块的放大」。
2. **hook 先行**：每章开篇必须是一个真问题，不许「本章介绍 X 模块」式开篇。
3. **阶梯不跳级**：任何概念首现前，其前置概念必须已立（pedagogy-plan 概念首现表为门禁）。
4. **why 链完整**：每个设计决策的叙事必含「旧设计→痛点→方案→代价」四要素（素材来自 ARCHITECTURE.md）。
5. Phase 0/1 产物未经用户审批，不得动笔写任何章。
