## Findings

### ADV-1［ADVISORY·L2］稳态门（第三道）里 `num_blocks_to_allocate` 数的是哪笔账没交代——它不是第一道门那笔整序列数

- 定位：chapter.md L1209-L1218（引用 kv_cache_manager.py:L521-L527 片段，L1214 `required_blocks = num_blocks_to_allocate + watermark_blocks`）
- 问题：读者刚在 L954-L977（第一道门）见过同名变量 = **整条序列**的块数（apply_admission_cap=True）。但 pin 源码里两道门之间**重算了一次**：L510-L519 `get_num_blocks_to_allocate(num_tokens=num_tokens_need_slot, …)`——按本步要落槽的 token（已算＋新＋lookahead，封顶 max_model_len）、**不夹上限**，L524 用的是这笔。正文只说「随后与稳态判定合流」，同名变量的换绑不可见；读者会以为稳态门仍拿整序列数在比（那样稳态门将永远比第一道门严、第一道门形同虚设，推矛盾）。
- 证据：pin `source/vllm/v1/core/kv_cache_manager.py` L476-L485（第一次计数，full_num_tokens，apply_admission_cap=True）→ L510-L519（第二次计数，num_tokens_need_slot，无 cap 参数）→ L524。正文 L1144 有一句「运行中的增量预测不用夹」是唯一暗示，但没绑回 L1214 这笔。
- 违反：L2（组合公式每一笔要能答「此刻在哪个账」——这里恰是被盖住的换绑点）
- 修法（定点，≤3 句）：在 L1216 引文后加一句：「这笔 `num_blocks_to_allocate` 已换过账：源码在两道门之间按本步重算（L510-L519，已算＋新＋lookahead 的槽位需求、不夹上限）——第一道门查整条序列装不装得下，这一道查本步增量够不够，一次 `allocate_slots` 调用里两道先后都过。」

### ADV-2［ADVISORY·口径］m4 表 PP 行「长度块」单位与前文探针行不一致，复算差一倍

- 定位：chapter.md L348（m4 表末行「护栏四 PP 取最小 | 两 worker 200 / 90 长度块 | 张量 13107200 → 5898240 B（缩到 90 页）」）
- 问题：探针行的「长度块」=131072 B（2 层模型一块，表头 L329-L345 由 len 1→131072 立住）；PP 行是每 worker 只持 1 层的景，1 块=单层页 65536 B，200 块×65536=13107200。读者按表头口径复算 200×131072=26.2 MB，对不上 13.1 MB。数字本身 trace 为真（traces/m4.json `guardrail4_pp_min`：tensor0 13107200→5898240、90 页），缺的是单位切换的一句话。
- 违反：数字口径（同表同名单位漂移，L2 同族）
- 修法（半句）：PP 行「关键数」格补「（PP 各 worker 持 1 层，此行 1 块＝单层页 65536 B）」。

### ADV-3［ADVISORY·跨章引用］「第 13 章算过…24 GB 卡权重 14 GB 池剩 8 GB」——ch13 里没有这三个数

- 定位：chapter.md L23
- 问题：ch13 实际内容只有 0.5 MB/token（ch13 L33：2×32×32×128×2=524288 B）与「权重吃掉一大半之后，剩下的每一 GB 都是 KV 的粮仓」（ch13 L9）；**没有** 24 GB/14 GB/8 GB。读者回翻 ch13 找这笔账会扑空。
- 违反：跨章口径一致（引用归属过头；数字本身与 ch13 的 0.5 MB/token=524288 B 一致、无矛盾）
- 修法（一句）：改为本章口吻——「第 13 章算过 0.5 MB/token 的账（Llama-2-7B FP16）；放到 24 GB 的卡上，权重吃掉 14 GB，池只剩大约 8 GB，每一 GB 都金贵。」

### ADV-5［ADVISORY·L1 同族］m13 稳态行「12 token 恰在窗口侧」复算对不上——53 个窗外 token 后直观只得 11

- 定位：chapter.md L1076（m13 表稳态行「…53 / 13 | [NULL×13, …] | 3 / 60（12 token 恰在窗口侧）」）
- 问题：skipped=53 ⟹ 窗外 token 0..52，直观在册 53..63 共 **11** 个；「12」是块粒度的 12 个槽位（tokens 52-63，52 号 token 已在窗外但与窗内同块、被整块拖住——恰是本章 +1 错位概念的实例，但这里没点）。trace 字段 `tokens_in_window: 12` 为真源，槽位/token 未分。
- 违反：数字口径 gloss（读者用正文公式复算 64−53=11 与 12 打架）
- 修法（半句）：括注改「实持 3 块＝tokens 52-63 共 12 个槽位（窗外 53 个，52 号 token 与窗内同块被整块拖住）」。

### ADV-6［ADVISORY·路标差一］「两节之后『SWA 的还账方式』细讲」——实际是紧邻的下一小节

- 定位：chapter.md L979（第一道门 m10 表引语）
- 问题：null 占位详解在 L991 的 `### SWA 的还账方式`，是 m10 所在 `### 第一道：整序列准入门`（L918）的**下一**小节，中间无任何小节。「两节之后」差一。
- 违反：L1 同族（重构/编排后的指针漂移；ch13 教训的正文版）
- 修法（一词）：改「下一小节」。

### ADV-7［ADVISORY·L4 精确性］「预约之和 ≤ 池 ⇔ 峰值实持之和 ≤ 池」的 ⇔ 方向过强，安全只需 ⟹

- 定位：chapter.md L1144（prose 转写；嵌入源码注释 L1136 的 `<=>` 是 pin 逐字、不可动）
- 问题：逐请求峰值实持 ≤ cap ⟹ 「Σ预约 ≤ 池」⇒「Σ峰值 ≤ 池」成立；反向不成立（人人预约到 cap、无人用满时 Σ峰值 ≤ 池 而 Σ预约 > 池）。prose 用 ⇔ 表「两道检查可互换」会绊住较真的读者；放行安全只需要单向蕴含。
- 违反：L4（不变量/等价断言要经得起反例推敲）
- 修法（半句）：prose 改「于是「预约之和 ≤ 池」⟹「峰值实持之和 ≤ 池」，放行安全（反向不必成立：预约比峰值保守，正是要的）」。
